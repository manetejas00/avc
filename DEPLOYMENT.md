# Runtime requirements and audit notes

The consultation form, admin login/dashboard, private e-book vault, market cache and scheduled news ingestion require the Express server and a writable SQLite database. Uploading only `dist/` to PHP/static hosting does not provide those features. Use a supported Node runtime with the installed `better-sqlite3` native addon, run `npm run build`, then `npm start`. Run behind HTTPS with a reverse proxy that preserves the original Host header. The PHP files provide market/news fallbacks only.

Set `NODE_ENV=production`, a random `JWT_SECRET` of at least 32 characters, `DATABASE_URL` outside the public web root, and provider keys (`INDIAN_API_KEY`, `MARKETAUX_API_KEY`, optionally `COINGECKO_DEMO_API_KEY`) on the server. Set bootstrap admin email/password only for initial account creation; startup never resets existing credentials. Keep `.env`, database files and archives outside the served directory. Do not upload the old local `dist.zip`; it is not regenerated by the audit.

Provider keys are server-only. Never use a `VITE_` prefix for secrets. PHP hosting needs corresponding environment variables and cURL. The `.htaccess` files require Apache rewrite/header support; Express does not interpret `.htaccess`. Only serve the `dist` folder or proxy requests to Express; do not expose the repository directory. Test and private routes send noindex headers where the configured server supports them.

No production deployment is performed by this audit. Existing credentials and database records must be preserved. Git untracking does not remove secrets from past commits; previously exposed credentials require owner-managed rotation and, if necessary, coordinated history cleanup.

Regression checks: `npm test` uses the production SQLite driver. If its native binary is unavailable locally, Node 24 can run `AUDIT_SQLITE_BUILTIN=true` with the test command; this selects a test-only SQLite adapter, not a production fallback. Browser automation in `tests/browser-audit.cjs` accepts `PLAYWRIGHT_MODULE_PATH`, `AUDIT_START_SERVER=true` (serve dist locally), `AUDIT_FLOWS_ONLY=true` and optional `AUDIT_SCREENSHOTS=true`. External providers are deterministic fixtures during that audit.

# Deployment Guide

This document outlines the steps to deploy the application to Hostinger using SSH or Git Auto-Deploy.

## Hostinger connection details

Store the server host, port, username, and SSH key securely outside this repository. Use the deployment details in the Hostinger control panel or your team's password manager.

---

## Method 1: Git Auto-Deploy (Current Setup)

You currently have Hostinger configured to pull from your GitHub repository (`manetejas00/avc`) directly into the `public_html` root directory.

### 1. Push changes to GitHub
Whenever you make changes, build the app locally and push everything (including the `dist` folder) to the `main` branch.
```bash
npm run build
git add src dist
git commit -m "Update website"
git push origin main
```

### 2. Fix the Hostinger Document Root
Because Hostinger Git clones the entire repository into `public_html`, the actual compiled website files are placed inside `public_html/dist`. You **must** configure Hostinger to serve this folder instead of the root folder.

1. Go to your Hostinger hPanel -> **Websites** -> **Manage**.
2. Find **Advanced** (or Domain Settings) and look for **Folder Index Manager** or **Document Root**.
3. Change the **Document Root** from `public_html` to **`public_html/dist`**.
4. Save the changes. Your website will now load the compiled Vite app correctly!

## Method 2: Manual Upload via SCP

If you prefer to bypass Git and upload the built files directly over SSH:

### 1. Build the Application locally
```bash
npm run build
```

### 2. Upload Files to Hostinger
Run the following command to securely copy the files. (If your SSH key is set up locally on this machine, it won't ask for a password).
```bash
scp -P 65002 -r dist/* u382139760@82.112.239.95:/home/u382139760/domains/test1.avinyacarefoundation.org/public_html/
```

## Method 3: Manual Upload via FTP

You can also use an FTP client (like FileZilla or SmartFTP) to upload your files.

### FTP credentials

Retrieve FTP host, username, port, and password from Hostinger or the team's password manager. Never save credentials in this repository. Rotate any credential that was previously recorded here.

### Steps
1. Open your FTP client and connect using the credentials above.
2. Run `npm run build` locally to generate the `dist` folder.
3. Open the `public_html` folder in your FTP client.
4. Upload all the contents **inside** your local `dist` folder directly into the `public_html` folder on your server.
